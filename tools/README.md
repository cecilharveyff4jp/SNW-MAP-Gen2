# SNW-MAP-Gen2 マップデータ半自動更新ツール（tools/）

同盟ランキング（総力）のスクショから、各メンバーの `power`（総力）を D1 に半自動反映するための道具一式。

## 前提のPC構成

- **保守用PC（このPC）**… DB更新・スマホ接続(adb/scrcpy)を行う。本ツールはここで完結する。
- **開発用PC**… アプリ開発・デプロイ専用。**本ツールは開発PCに一切依存しない。**

スマホに触れられるのは保守用PCだけなので「画面キャプチャ」だけは必ずこのPCで行う。
抽出・照合・DB反映はチャット(Claude)でも保守用PCでも実行できる。

**依存はこのフォルダで独立している**（`tools/package.json`）。アプリ本体の `package.json` は汚さない方針。
初回だけ `cd tools && npm install`（画像解析用の `pngjs` が入る）。
`tools/` 一式はこのPCローカル運用でリポジトリには入れない（`.git/info/exclude` でこのPCだけ除外済み）。

## 全体の流れ

画面の取得元は2通りある。**PC の Google Play Games でゲームを開いているならスマホは要らない**
（→「GUI（`capture-gui-gp.ps1`）— Google Play Games 版」）。以下はスマホ＋adb の従来ルート。

```
[保守用PC] adbでランキング画面を連続キャプチャ  → capture-ranking.mjs
          （または scrcpy 画面をそのままスクショ）
        │
        ▼ 画像をこのチャットに貼付
[チャット] Claudeが「名前＋総力」を抽出 → ranking.json
        │
        ├─(A) チャット/保守PCから直接反映 → apply-ranking.mjs （要 APIトークン）
        └─(B) SQLを作って流す            → ranking-to-sql.mjs → wrangler で適用
```

## GUI（`capture-gui.ps1`）— 上の流れをボタンで通す

デスクトップの **SNW撮影.lnk**（中身は `capture-gui.cmd` → `capture-gui.vbs`）。
撮影メニューを選んで、①撮影 →②解析 →③ドライラン →④実行 を左から順に押すだけ
（［①〜③を通しで］1ボタンで④の直前まで進む）。

②の解析は2通りあり、**［解析はチャットでやる］が既定ON**。
ON なら切り出し後にお題をクリップボードへ入れ、JSON が置かれるまで待つ（チャットに貼る → Claude が読んで書く → GUI が検知）。
OFF なら `claude.exe -p` をヘッドレスで起動して同じことを無人でやる。

```
① 撮影      capture-*.mjs           端末を adb で操作して連続キャプチャ
② 解析      crop-*.mjs → claude -p  読む面積を削ってから画像を読ませ、JSON を書かせる
            → verify-ranking.mjs    順位1..N連続 / 総力単調減少 / 名前 を機械検査
③ ドライラン apply-*.mjs            DBと照合するだけ（書かない）
④ 実行      apply-*.mjs --apply     D1へ反映
```

**④は「③が合格」かつ「未一致0・要確認0」でなければ押せない。** 読み違いは必ず③に出るため。
実測(2026-07-28)：ヘッドレス解析は総力68件を1つも間違えなかったが、名前の装飾記号
（`ɛʋ` `୨୧` `ෆ` `⚔`）を残すことがあった。装飾が残ると名前が一致せず③で未一致に落ちる。

- 費用と時間の目安（ランキング1回）: 撮影40秒 / 解析84秒・約 $0.43 / 反映数秒。
- 接続は先に `wifi-gui.ps1` で済ませておく（`tools\.adb-target` を読む）。USB接続なら不要。
- `claude.exe` は VSCode 拡張同梱のものをワイルドカードで探す。`$env:CLAUDE_EXE` で上書き可。
- **`--allowedTools` を明示的に渡している。** このワークスペースは trust されていないため、
  `-p` 実行時は `.claude\settings.json` の permissions が無視される（起動時に警告が出る）。
- 壊れやすい所（実行ファイルの解決・工程のパス・出力ストリーミング）は画面を出さずに検査できる:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\capture-gui.ps1 -SelfTest -SelfTestOut out.txt
```

## GUI（`capture-gui-gp.ps1`）— Google Play Games 版（スマホ不要）

**PC の Google Play Games でゲームを開いている場合はこちら。** スマホも adb も要らない。
起動は `capture-gui-gp.cmd`（→ `capture-gui-gp.vbs`）。画面と工程は上のスマホ版とまったく同じで、
違うのは **①撮影の経路だけ**。②以降（切り出し・解析・検証・ドライラン・反映）は同じツールを呼ぶ。

|  | スマホ版 | Google Play Games 版 |
| --- | --- | --- |
| 画面の取得 | `adb exec-out screencap` | ウィンドウの範囲を画面からコピー |
| スクロール | `adb shell input swipe` | マウスのドラッグ（`SetCursorPos` + `mouse_event`） |
| 撮影ツール | `capture-ranking.mjs` | `capture-ranking-gp.ps1` |
| 準備 | Wi-Fi/USB 接続 | 不要（ゲームを起動しておくだけ） |
| 撮れるもの | ランキング / ID / 都市カード / 全部入り | **ランキング（総力）のみ** |

実測(2026-08-07): 66人ぶんで **21枚 / 50秒**。最下部を検知して自動停止する。
1..66位を1件も落とさず、ドライランで 61件一致・未一致5件（すべて改名候補）まで確認済み。

### 使う前に（ここだけ注意）

- **ランキング画面を開き直して一番上に戻してから撮ること。**
  ★**戻す方向（下向きドラッグ）はゲームが受け付けない**（実測）。上向き＝先へ送る方向しか通らないので、
  途中から撮り始めるとその手前が丸ごと欠ける。GUI は2枚以下で終わった場合に警告して止まる。
- 撮影中は**ゲームの窓が前面に出て、マウスカーソルが動く**（終わると元の位置に戻す）。
  画面をそのままコピーするので、**ゲームの窓を他のウィンドウで隠さないこと**。
- ゲームの窓が複数あると対象を決められないので、1つだけにする。
- ［下見］ボタンで、撮らずに「いま何が映っているか」を確認できる（`tools\shots\gp-probe\`）。

### 撮っているのは「窓」ではなく子ウィンドウ `CROSVM_1`（＝ゲームの描画面）

Google Play Games の窓には、状況によって**タイトルバーと左のサイドツールバー**が付く。窓のサイズも
全画面／半面で変わる。親ウィンドウを撮って「黒くない所＝中身」で切り詰める作りにしていたら、
**ツールバーを中身と誤認して切り出しが全部ずれた**（実測 2026-08-07: 順位バッジの代わりに
ツールバーのアイコンが写ったシートができ、そのキャプチャは丸ごと使えなかった）。

子ウィンドウ `CROSVM_1` の矩形はゲームの絵と1対1（実測 561x999 ＝ ゲーム内解像度 608x1080 と同じ比）。
ツールバーが出ていようが、窓を伸縮しようが、同じものが撮れる。**窓幅が変わっても切り出しの割合
指定はそのまま効く**（GUI が渡している `--y0/--y1/--hmin/…` は変更不要）。

撮影中に窓の大きさが変わった場合も、その場で基準を取り直して続行する（ログに出る）。

### なぜ画面コピーで、PrintWindow ではないのか

`PrintWindow(PW_RENDERFULLCONTENT)` なら裏に回った窓でも撮れるので最初はそちらを使ったが、
**古いフレームがそのまま返ることがある**（実測: 実際にはスクロールしているのに、何枚撮っても
まったく同じ画像＝差分 0.00% が返り続けた）。撮れた画像が今の画面と一致している保証が無ければ
取りこぼしを検知できないので採用しない。どのみち入力を送るために前面化するため、画面から直接撮る。
裏で撮りたいときだけ `-Capture window` で切り替えられる。

### 単体で回す / 調整する

```powershell
# 下見（ゲームには触らない。窓の大きさと黒帯の量を出して画像を2枚置く）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\capture-ranking-gp.ps1 -Probe -Out tools\shots\gp-probe

# 撮影だけ
powershell -NoProfile -ExecutionPolicy Bypass -File tools\capture-ranking-gp.ps1 -Out tools\shots\rank-gp

# 切り出し（GP版は既定値と別のパラメータが要る。GUI が自動で付けている値と同じ）
node tools\crop-rank.mjs --in tools\shots\rank-gp `
  --th 0.45 --gap 4 --y0 0.172 --y1 0.882 --hmin 0.080 --hmax 0.110 `
  --badge-x0 0.035 --badge-x1 0.190 --text-x0 0.330 --text-x1 0.980

# 配線の自己診断（画面を出さない）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\capture-gui-gp.ps1 -SelfTest -SelfTestOut out.txt
```

★ **`--gap 4` を落とさないこと。** ここが GP 版でいちばん壊れやすい。行間の隙間が 11〜12px しか
無いため、既定の `--gap 10` だと隣の行と繋がって「高すぎる帯」として捨てられ、1枚から取れる行数が
0〜6行と暴れる（＝順位が丸ごと消える）。`--th` は 0.35〜0.5 ならどれでも同じ結果になるが、
0.6 まで上げると金色の1位だけが割れて消える。

保存される画像は**左右の黒帯を落とした中身だけ**（実測 960x1032 の窓 → 577x1029）。
黒帯の幅は窓の大きさで変わるので、入れたままだと上の割合指定が窓サイズ依存になってしまう。

### 撮れないもの

**都市カード（`capture-cards.mjs`）は GP 版に未対応。** 郊外マップで都市を順にタップして
カードを待つ操作が要るため、座標を入れたいときは従来どおりスマホ＋`capture-gui.ps1` を使う。

ID取得は **GP版でも撮れる**（次節）。2026-10-08 までは未対応だったが、同盟ランキングから
領主ファイルに入れることが分かったので `capture-ids-gp.ps1` を足した。

## 領主ファイルの巡回 — `capture-ids-gp.ps1`（GooglePlay版）

同盟ランキングから全員の **ゲームID と FIREレベル** を取る。ゲームIDは不変なので、これがあると
**改名・新規加入・脱退を推測ではなく確定できる**。総力の増え方から改名を当てる方法は、総力が
近い人が2人いると原理的に分離できない（実測 2026-10-08: `戦闘員S`/`戦闘員まるも`、
`ﾏﾙｺｽ`/`とっとこﾄﾑ太郎` の2組が決められなかった。IDを取ったら即決した）。

### 1人ぶんの操作

```
ランキングの行をクリック → ポップアップ → ［確認］ → 領主ファイル → 左上の ← で戻る
```

```powershell
# 下見（ゲームには触らない。行の検出結果とポップアップの有無を出す）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\capture-ids-gp.ps1 -Probe -Out shots\ids-gp

# 試運転（先頭3人だけ）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\capture-ids-gp.ps1 -Out shots\ids-gp -Limit 3

# 本番
powershell -NoProfile -ExecutionPolicy Bypass -File tools\capture-ids-gp.ps1 -Out shots\ids-gp-YYYYMMDD

# 取りこぼしが多いとき（重複判定をせず画面に出た行を全部撮る。約2倍遅いが落とさない）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\capture-ids-gp.ps1 -Out … -NoDedupe
```

切り出しは `crop-ids.mjs` を GP 版の割合で呼ぶ（スマホ版の既定値とは別）。
**`--no-dedupe` を付けること**（撮影側で重複を落としているうえ、`crop-ids.mjs` のハッシュ判定は
別人を同一と見て捨てたことがある）。

```powershell
node tools\crop-ids.mjs --in tools\shots\ids-gp-YYYYMMDD --out tools\shots\ids-gp-YYYYMMDD\sheets `
  --no-dedupe --x0 0.34 --x1 0.995 --y0 0.692 --y1 0.806 --per-sheet 14 --cols 2
```

### ★ここだけ注意（実測で踏んだもの）

- **［削除する］（同盟追放）が同じポップアップに並んでいる。** 押したら取り返しがつかない。
  ツールは押す直前に「その画素が本当に青いか」を確かめ、青くなければその人を飛ばす
  （［削除する］は橙なので弾ける）。**座標を決め打ちする実装に変えないこと。**
- **ポップアップの出る位置は毎回変わる**（押した行に付いて動く）。毎回「純白の**連結成分**」で
  箱を探す。行ごとの白画素数で箱を切ろうとするとボタンの段で白が途切れ、240px の箱が 19px に割れる。
- **自分自身（セシル）はランキング最下部に固定表示されていて、押しても領主ファイルに飛ばない。**
  中心が画面の 0.88 より下の行は自動で除外している。自分のIDは DB から補う（`462237784`）。
- **リストは先頭に戻せる。** 下向きドラッグはゲームが受け付けないが、ランキング左上の **←** →
  同盟画面 → **［総力ランキング］**（中身の割合で約 0.262, 0.840）で開き直せば先頭から撮り直せる。
  同盟画面にはメンバー数（例 `80/100`）も出ていて、ランキングが全員ぶんかの確認に使える。

### スクロールはホイール（★ドラッグは使わない）

**ホイールは 1ノッチ = きっかり 44px** で完全に決定的。ドラッグは指のスワイプとして渡るので動くが、
**慣性が乗って送り量が毎回ぶれる**ため、どこまで進んだかが分からなくなる。

実測 2026-10-08（窓 561x999 / 中身 561x989 / 行の間隔 105.5px、1ノッチずつ10回）:

| 回 | 1 | 2 | 3〜10 |
| --- | --- | --- | --- |
| 送り量 | **0px** | 38px | **44px**（完全に一定） |

6ノッチずつ送ったときも 1回目 219px（吸われ込みのぶん）、2回目以降 **263px = 6×44** で一定。

- **リスト最上段では1ノッチ目が吸われて 0px になる。** 最下部の判定に「動かなかったら終わり」を
  使うなら、1回で切らずに**2回続けて0px**を条件にすること。
- 既定の **12ノッチ = 526〜528px ≒ 5.0行**。画面には6行出るので必ず1行以上重なる＝飛ばしようがない。
- **カーソルをリストの上に置いたまま回すこと。** ホイールはカーソルの下にある物に届く。
- ★**回す前に必ず窓を1回クリックすること。** クリック（`mouse_event`）はカーソルの下の窓に
  位置で届くが、**ホイールはフォーカスのある窓にしか届かない**。`SetForegroundWindow` だけでは
  足りない。実測 2026-10-08: 画面は正常なランキング（ポップアップ無し）なのに、**36ノッチ投げて
  1pxも動かない**状態になった。直前に列見出しの帯を1回押すと以後きちんと動く。
  押す場所は列見出し「順位／領主／総力」（中身の割合で 0.50, 0.148）。**押しても何も起きない**
  ことは実測で確認済み（クリック後の移動が純粋な平行移動で、並び替えも画面遷移も起きない）。
  `capture-ids-gp.ps1` は `-FocusX/-FocusY` でこれを毎回入れている。
- ※`capture-ranking-gp.ps1` の冒頭には「★4 ホイールは効かない」と書いてあるが**あれは誤り**。
  効かなく見えた原因は (a) ［確認］のポップアップが開いていた (b) 人が同時にマウスを触っていた。
  ランキングの連続キャプチャ側はまだドラッグのままなので、直すならここと同じ手が使える。
- 旧方式に戻すなら `-Scroll drag`。

### 既撮の判定は「絶対位置」（★見た目で比べない）

送り量が決定的に測れるので、**画面が何画素動いたかを毎回測って積算し、各行の「リスト先頭からの
絶対 y」で既撮かどうかを判定する**。1手につき「新しい行を1人撮る」か「1回スクロールする」の
どちらかだけを行い、毎回撮り直して位置を測り直すので、領主ファイルから戻ったときにリストが
動いていても自動で追従する。

```
絶対y: 230, 336, 440, 546, 652, 756 →(526px送り)→ 862, 967 …  間隔105〜106pxで連続
```

★**送り量の測り方で踏んだ罠（ここが一番やられた）。**

**候補ごとに比較する画素数を変えてはいけない。** 最初は「2枚の重なった部分だけを比べて
RMS が最小の dy を採る」実装にしたが、これだと**大きく送ったとき（重なりが1.5行ぶんしか
残らない）に dy=0（重なり最大）の不正解が勝つ**。リストは行が周期的でレイアウトが同じなので、
dy=0 でもそこそこ合ってしまう。実測 2026-10-08:

- 526px(12ノッチ)送り: 本当は動いているのに **0px** と出た。残差は 20前後（正解時は 4〜6）
  なのに、それが最小だった。巡回がリストの半分で「最下部」と誤判定して終了。
- その前の版でも、最下部手前の1回だけ 376px → **165px** と誤測し、絶対位置が2行ぶん足りなく
  なって `スマートEX` と `パックン` が「撮影済み」と誤判定されて落ちた。

→ **新しい画面から固定高さの短冊(テンプレート)を切り、古い画面の上を滑らせて探す**作りに変更。
どの dy でも比較画素数が同じになるので公平に比べられる。短冊は上から 0.20H・高さ 0.22H なので
**測れる送り量の上限は約 445px**。だから **1回の送り量は 6ノッチ(264px) にしてある**
（12ノッチ=528px は測定上限を超えるので使わないこと）。

残り2つの保険（どちらも余分に数枚撮るだけ。後段がゲームIDで重複を落とす）:

- 残差が `-ShiftRmsMax`（既定12）を超えた画面は、絶対位置を信用せず**見えている行を全部撮る**
- 最下部に着いたらそこで止めず、**見えている行を全部撮ってから**終わる

☠ **以前は「行の見た目」を格子に潰したハッシュで判定していたが、これは当てにならない。**
名前だけの帯で取ったとき、短い名前（`りつき` `kina` `Juhi` `なぎさ` `トントゥ` `かいさん`
`しゅてん` `わのさん` `戦闘員一撃万枚`）の**9人が「重複」と誤判定されて丸ごと落ちた**
（79人中70人しか撮れなかった）。帯のほとんどが無地なので、正規化すると雑音が支配して
別人同士の距離が縮む。総力の数字まで入れて改善したが、それでも5人落ちた。
絶対位置なら名前の長さに一切影響されない。

実測 2026-10-08（在籍80人 / 自分を除く79人が上限）:

| 方式 | 1回で揃った人数 | 備考 |
| --- | --- | --- |
| ドラッグ＋見た目ハッシュ | 70 → +4 → +5 | **3回ぶん合流してやっと79人** |
| ホイール＋絶対位置 | **79（1回で全員）** | 訪問80行・失敗1（=セシル）・測定警告0 |

ホイール版の1巡は 85枚/スクロール31回。絶対位置は 230→8541 まで105〜106px間隔で連続し、
唯一の隙間（2650→2860）が**セシルの行**＝押しても領主ファイルに飛ばないので正常。
読み取った79人は、別方式で取ったデータとゲームID・名前・FIREレベルが**完全に一致**した。

★それでも **`verify-ids.mjs` の照合は必ず通すこと。** ポップアップが出ない等の取りこぼしは
別の原因で起こり得る。複数回ぶんは `merge-runs.mjs` でゲームIDで合流できる。

### 取りこぼしの検知（★これをやらないと気付けない）

**先にランキングを撮って名前の一覧を作っておき、領主ファイルと名前で突き合わせる。**
枚数では絶対に分からない（重複スキップの数と区別が付かない）。

```powershell
node tools\merge-runs.mjs --out tools\profiles-all.json tools\profiles-a.json tools\profiles-b.json
node tools\verify-ids.mjs --profiles tools\profiles-all.json --ranking tools\ranking-YYYYMMDD.json --self ｾｼﾙ
```

### 揃ったあとの流れ

```powershell
# ① ランキングの各行に gameId / fcLevel を合流（★これが無いと改名が二重登録になる）
node tools\merge-profiles.mjs --ranking tools\ranking-X.json --profiles tools\profiles-all.json --out tools\ranking-X-ids.json

# ② 改名/新規加入/脱退の仕分け（ゲームIDなので確定）
node tools\classify-members.mjs --profiles tools\profiles-all.json --map 1

# ③ 新規メンバーを仮設置したいとき: 基準物の周りの空きマスを探して座標を付ける
node tools\plan-placement.mjs --map 1 --count 8 --size 2
node tools\set-coords.mjs --ranking tools\ranking-X-ids.json --coords tools\new-coords.json --out tools\ranking-X-final.json

# ④ 検証 → ドライラン → 反映
node tools\verify-ranking.mjs --ranking tools\ranking-X-final.json
node tools\apply-ranking.mjs --ranking tools\ranking-X-final.json --create-new
node tools\apply-ranking.mjs --ranking tools\ranking-X-final.json --create-new --apply

# ⑤ 脱退者を「その他」に（都市は消さない）→ 都市件数＝在籍人数になる
node tools\retire-members.mjs --ranking tools\ranking-X-final.json --map 1          # ドライラン
node tools\retire-members.mjs --ranking tools\ranking-X-final.json --map 1 --apply

# ⑥ 仮設置が重なっていないか確認
node tools\check-overlap.mjs --map 1
```

★⑤は**ゲームIDで判定する**こと。名前で判定すると改名した人を脱退と誤認して全員の型を壊す。
`retire-members.mjs` は ranking に gameId が無い行があると止まる。

照合キーの優先順位は **game_id（ゲーム内ID・不変） > 名前完全一致 > 名前の緩い一致(loose)**。
ゲーム内で改名が多いため、ID があれば最優先で使う。名前はサーバ保存時に半角化（`toHalf`）
されるので、本ツールも同じ正規化で突き合わせる。プロフィール名の同盟タグ `[SNW]` と
末尾のレベル `（42）` は照合前に自動除去。装飾記号入りの名前は loose で拾い、確実でない
ものは *要確認* に回して自動では書き換えない。

★ 名前は DB の **`label`** カラムに入っている（`member_name` は未使用）。本ツールは
`label` を照合名として使い、改名追従・新規登録も `label` に書く。`label` も保存時に半角化。

ID 照合の副作用として、ID一致で名前が変わっていれば `label` を更新（改名追従）、
DB に `game_id` が無ければ今回の ID で補完する。

抽出時の注意：ゲームUIの装飾（名前の右上に付く小さな称号/吹き出し、例「maru Love」）は
名前の一部ではないので除く。これを含めると別名として未一致になる。

データ源の使い分け：
- **ランキング一覧** … name, power（正確なフル数値）。一覧は速い。
- **郊外(マップ)の都市カード** … name, x, y, power（正確）。タップで座標が出る。
- **都市名横の星バッジ** … fcLevel（炉/FCレベル）。
- **領主ファイル** … gameId, name, **fcLevel**。総力は丸め(644.8M)なので総力は一覧/カード優先。
  入口は2つ: 郊外の都市カードのアバター→、または**同盟ランキングの行→［確認］**（GP版はこちら）。
  FIREレベルは城アイコンの右のバッジ。FC到達前は `Lv.27` のような表示で、DBにも裸の数字で入る。

入力JSONの各キーはすべて任意：`name, power, gameId, x, y, fcLevel`。混在OK。

座標について：タップして出る X/Y は DB の `anchor_x`/`anchor_y`（フットプリント最小角）にそのまま対応。
- 新規：座標があれば実座標に配置（placed=1）、無ければ未配置プール（placed=0）。
- 既存：座標差分は**自動で動かさない**。`apply-ranking` は差分を提示するだけ、反映は `--sync-coords` 明示時のみ。
  `ranking-to-sql` は差分を `coords.sql` に別出しするので、確認して流す。

（今後の拡張）旗(1×1)・同盟資材(2×2)などもタップで座標カードが出るため、都市以外の全種別も
座標＋種別で登録・同期できる。これらはIDや一意名が無いので「種別＋座標」で照合する予定。

処理は2系統：
- **既存メンバー** … `power`（総力）を反映
- **新規メンバー（DBに居ない）** … 未配置プール（`placed=0`）に CITY として登録。座標はランキング画面に無いので持たせず、アプリの「未配置」からカードを選んで地図に配置する。
- **反映できなかった人** … レポート(`apply-report.json` / `report.txt`)に必ず残す（`newMembers`＝新規候補、`needsReview`＝要確認、`notInRanking`＝ランキング未出現のDB既存）。

## 0. スマホをPCに繋いでミラーリングする

### 0-Z. USB（現在のメインルート）

USB を挿して、デスクトップの `scrcpy.lnk` をダブルクリックするだけ。
うまくいかない時のログを読みたい場合は `tools\mirror-usb.cmd` を使う。

★ **ショートカットの引数には必ず `-d` を付ける。** 引数なしの `scrcpy.exe` は、adb にデバイスが
2つ以上見えていると「どれか決められない」で**即終了する**（ウィンドウが一瞬で閉じる正体はこれ）。
前回の Wi-Fi セッションの残骸 `192.168.0.x:ポート  offline` が1つ残っているだけで発生する。
`-d` は USB のデバイスを明示的に選ぶので、残骸があっても起動する。

```
scrcpy.lnk の引数:  -d --stay-awake
```

残骸そのものを消したいときは `adb disconnect`（引数なしで全部切る）。`mirror-usb.cmd` は
起動前にこれを実行してから `-d` で立ち上げ、失敗時は `pause` してエラーを読めるようにしてある。

### 0-A. Wi-Fi・GUI（USB を挿したくない時）

`tools\wifi-gui.cmd` をダブルクリック。

1. 端末の 設定 → システム → 開発者向けオプション → **ワイヤレスデバッグ** を開く
2. 画面上部の「IP アドレスとポート」を GUI に入れる
   （`192.168.0.52:33593` を IP 欄にそのまま貼れば自動で分割される。`-` 区切りでも可）
3. **［接続］** を押す → 成功したら自動で scrcpy のミラーリングまで起動する

［接続］が内部でやること（手作業だと毎回ここで詰まっていた）:

- 先に **TCP 到達チェック**。届かなければ「ポートの値が古い」と即断して案内する
  （ワイヤレスデバッグを OFF→ON するたび、また Wi-Fi 再接続のたびにポートは変わる）
- `state=offline` に落ちたら **disconnect → 再 connect**、駄目なら **kill-server → 再 connect** まで自動
- 成功したら `tools\.adb-target` を CLI 版と同じ形式で保存（以降 `. tools\adb-env.ps1` が使える）

下段の「初回のみ」欄は未ペアリング時のペア設定用。普段は触らない。

★ **`.cmd` / `.vbs` は ASCII のみで書くこと。** cmd.exe はバッチファイルを OEM コードページ(932)で読むため、
UTF-8 の日本語コメントが化けて後続行まで壊れる。実際にこれで「ダブルクリックしても一瞬窓が出て消えるだけ」
になった（PowerShell が起動していなかった）。

★ 逆に **`wifi-gui.ps1` は UTF-8 BOM 付き**で保存する。BOM が無いと Windows PowerShell 5.1 が ANSI として読み、
日本語が化けて構文エラーになる。同じフォルダで .cmd と .ps1 の要求が逆なので注意。

★ **起動は必ず `wifi-gui.vbs` 経由**（ショートカットも `.cmd` もこれを呼ぶ）。
`powershell.exe` を直接起動すると **GUI の裏に Windows Terminal の窓が残り、それを閉じると GUI ごと落ちる**。
効かなかった手（同じ回り道をしないための記録）:

| 試した手 | 結果 |
| --- | --- |
| `ShowWindow(GetConsoleWindow(), SW_HIDE)` | 消えない。Win11 の既定コンソールは Windows Terminal で、窓を持つのは `WindowsTerminal.exe` 側。`GetConsoleWindow()` が返すのは実体のないダミー |
| `FreeConsole()` | Terminal の窓は残る（保険として ps1 に残してある） |
| `powershell -WindowStyle Hidden` | ショートカットから起動すると Terminal の窓が残る |
| **`wscript.exe wifi-gui.vbs`（`Run(..., 0, False)`）** | **窓が1つも作られない。これを採用** |

### 0-Y. Wi-Fi が遅いとき（回線の実測と端末側の設定）

**まず測る。** 接続の成否だけ見ていると原因の切り分けに何十分もかかる。

```powershell
. tools\adb-env.ps1
node tools\link-check.mjs          # PNG を数枚取って ms / Mbps / 判定を出す（端末は変更しない）
node tools\link-check.mjs --raw    # raw も測る（遅い回線では固まるので普段は不要）
```

判定の目安（PNG 1枚あたり）: **〜1秒 良好 / 1〜3秒 監視は可・ミラーリングは重い / 3秒〜 実用外**。

★ **端末を充電器に挿し、開発者向けオプションの「充電中は画面を ON のまま」を ON にする。**
画面が消えると Android の Wi-Fi 省電力が効いて、ping が数百ms＋パケットロスという状態になる。
2026-07-27 の実測では **RTT 764ms / ロス 50%** まで悪化し、adb が繰り返し offline に落ちた。

このときの環境（記録）:

| 測定 | 値 |
| --- | --- |
| PC↔ルーター | 良好（電波95%、130/144Mbps） |
| ルーター | **2.4GHz のみ**（5GHz の SSID なし）、ch11・利用率 39〜47% |
| `watch-warehouse.mjs` 1判定の転送量 | raw **4.43MiB**（720×1612×4） |
| 荒れた回線で raw を1枚取得 | **54.5秒かかって接続断** |
| 同じ都市画面の PNG | **1295KB**（約3.5分の1） |

★ **PNG のサイズは画面の中身で大きく変わる。** 設定画面のような平坦な絵だと約140KB まで落ちるが、
監視対象の**都市画面は絵が細かいので 1.3MB 前後**になる。平坦な画面で測った値を基準にすると
見積りを4倍間違える（実際に一度間違えた）。回線を評価するときは**ゲーム画面を出したまま**測ること。

回線が回復した後の実測（ping 12ms / ロス0%、都市画面）:

| 方式 | サイズ | 所要 |
| --- | --- | --- |
| raw | 4.43MiB | 2430ms |
| PNG | 1295KB | 1621ms |

raw と PNG は**画素データとして完全に等価**であることを実機で確認済み
（同一画面の平均RGB・`hudBrightness` が一致。チャンネル順も同じ）。

このため `watch-warehouse.mjs` は接続の種類で取得方式を変える（後述の「5. 監視モード」参照）。
`capture-ranking.mjs` は元から PNG なのでこの回線でも成立する。

### 0-B. CLI（connect-wifi.mjs）

USB を挿しっぱなしにせず、ワイヤレスデバッグ（Android 11+）で繋ぐ。

```powershell
node tools\connect-wifi.mjs          # 初回：手順を出しながら対話でペアリング
node tools\connect-wifi.mjs --auto   # 2回目以降：無入力で再接続
. tools\adb-env.ps1                  # ★接続後、キャプチャ前に毎回これ（環境変数を入れる）
```

対話モードの流れ（端末側の操作を1つずつ案内する）:

1. スマホの Wi-Fi をオン（PCと**同じネットワーク**）
2. 開発者向けオプション → **ワイヤレスデバッグ** を ON
3. 「ペア設定コードによるデバイスのペア設定」をタップ（ダイアログは**開いたまま**）
4. **IPアドレス**（`192.168.0.5:41234` 形式）を入力 ← mDNS 検出候補が出るので Enter でもよい
5. **PIN**（6桁のペア設定コード）を入力
6. 接続 → 端末名・解像度を表示して `tools\.adb-target` に保存

**IP・ポートが毎回変わる問題**：ワイヤレスデバッグは IP も 2 種類のポートも接続のたびに変わる。
このツールは固定値を覚えず、毎回 `adb mdns services` で「今の IP:ポート」を発見して繋ぐ。
そのため 2 回目以降は `--auto` だけで、IP が変わっていてもノー入力で繋がる。

★ ポートを間違えやすい：**ペアリングに使うのはダイアログ側のポート**で、
ワイヤレスデバッグ画面上部に出ている接続用ポートとは別物。混ぜると `pair` が失敗する。

★ **ペアリング（PIN）は端末＋PCの組み合わせにつき初回だけ。** 以後は connect のみ。
端末側で「ペア設定済みのデバイス」から解除した場合だけ、やり直しになる。

★ `adb-env.ps1` が入れる `ANDROID_SERIAL` は adb 標準の環境変数で、`-s` 未指定時に使われる。
おかげで `capture-*.mjs` は**一切変更なし**で Wi-Fi 端末を掴む（USB も同時接続時の取り違えも防げる）。

その他: `--status`（接続確認） / `--disconnect` / `--pair IP:PORT --code 123456` / `--connect IP:PORT`（個別実行）。

## 1. キャプチャ（保守用PC・このPC）

USB + scrcpy で端末がつながっていれば adb はそのまま使える（ワイヤレス設定は不要）。
Wi-Fi 接続にする場合は前節「0.」を先に実行する。
※ この手順を使う場合のみ、このPCに Node.js と adb が必要。準備なしで済ませたいなら
   scrcpy 画面をスクショしてチャットに貼るだけでもよい（抽出・反映はチャットで行う）。
ゲームで 同盟→ランキング→総力 を開いておく。

```bash
node capture-ranking.mjs --count 6 --out ./shots --swipe 540,1600,540,700
# ワイヤレスの場合のみ:  --connect <スマホIP:PORT> を追加

node crop-rank.mjs --in ./shots   # 撮影後に挟む。読ませる画像が 14枚→5枚（面積63%減）になる
```

★ `crop-rank.mjs` は**重複を除去しない**（実測で試した4手法がいずれも別人を潰したため）。
読み取り後は必ず **順位が 1..N で連続しているか**を確認すること。件数では取りこぼしを判定できない。

★ 行の検出は**アバターを除いた範囲**の明るさで行う。全幅で測ると、黒いアバターの人の行が
平均輝度を割って分断され、その人だけ静かに消える（実際に1位が消えた）。

- `--swipe x1,y1,x2,y2` は実機解像度に合わせて調整（下→上へスクロール）。
- 保存された `./shots/*.png` をこのチャットに貼れば、名前＋総力を抽出する。
- そもそも scrcpy 画面をそのまま画面キャプチャして貼ってもよい（この場合スクリプト不要）。

## 2. 抽出（チャット）

キャプチャ画像をチャットに貼ると、Claude が次の形式で `ranking.json` を返す：

```json
[ { "rank": 1, "name": "ゆうご太郎", "power": 644862328 }, ... ]
```

（名前末尾の「（42）」等のレベル表示は自動除去される）

## 3-A. チャット/PCから直接反映（apply-ranking.mjs）

認証情報は `tools/.env` に置く（`tools/` ごとリポジトリ管理外。雛形は `tools/.env.example`）：

```
CF_API_TOKEN=xxxx                                  # D1:Edit 権限のAPIトークン（必須）
CF_ACCOUNT_ID=5f894da3ef5e6384b8361ddf809b8a2e     # ★実質必須。理由は下記
# CF_DATABASE_ID は既定で snw-map-gen2 の 360d346e-... を使用
```

環境変数（`export` / `setx`）でも動き、そちらが優先される。VS Code の Python 拡張が「.env をターミナルに
取り込むか」と聞いてくるが、**有効にしない**こと（全ターミナルの環境変数にトークンが載る）。ツールは自前で読む。

★ `CF_ACCOUNT_ID` は省略できない：権限を **D1:Edit のみ**に絞ったトークンだと `GET /accounts` が 403 ではなく
**空のリスト**を返し、自動取得が失敗する。アカウントIDはダッシュボードのURL `https://dash.cloudflare.com/<ここ>/...`
で確認できる。トークンの権限を広げるより、IDを書く方が安全。

```bash
node apply-ranking.mjs --ranking ranking.json                          # ドライラン（既定・書き込まない）
node apply-ranking.mjs --ranking ranking.json --apply                  # power反映（exact一致のみ）
node apply-ranking.mjs --ranking ranking.json --apply --include-fuzzy  # loose一致も反映
node apply-ranking.mjs --ranking ranking.json --apply --create-new     # 未一致を新規都市として未配置プールに登録
```

安全設計：既定はドライラン。`--apply` の時だけ書き込む。exact一致のみが既定対象で、loose一致は `--include-fuzzy`、新規登録は `--create-new` を明示した時だけ。値が変わらない行は更新しない。処理後 `apply-report.json` に反映できなかった人を含む全結果が残る。

## 3-B. SQLを生成して自分で流す（ranking-to-sql.mjs）

D1 に触れずにSQLとレポートだけ作る。現行 objects は次で用意：

```bash
wrangler d1 execute snw-map-gen2 --remote --json \
  --command "SELECT id, member_name, power, type FROM objects" > objects.json

# out/update.sql      … exact一致の power UPDATE（そのまま流せる）

# out/review.sql      … loose/曖昧（確認してから）

```

## 4. 都市カードで座標を入れる（capture-cards.mjs → apply-cards.mjs）

ランキング画面には座標が無いので、新規メンバーは `placed=0`（未配置プール）で登録される。
これを地図に載せるための座標は「郊外マップで都市をタップして出るカード」から取る。

```bash
# ① 保守用PC: ウォッチ開始 → オーナーが郊外マップで都市を順にタップするだけ
node tools\capture-cards.mjs --out tools\cards\cap
#    カードを検知したら card_001.png ... と自動保存。終了は Ctrl+C。
# ② 画像をチャットに貼って「done cards」→ Claude が名前+X/Y+総力を読んで cards.json を返す
# ③ 反映
node tools\apply-cards.mjs --cards tools\cards.json                       # ドライラン（既定）
node tools\apply-cards.mjs --cards tools\cards.json --apply               # 未配置→配置(placed=1)＋総力/FC反映
node tools\apply-cards.mjs --cards tools\cards.json --apply --move-existing  # 配置済みの座標ズレも直す
node tools\apply-cards.mjs --cards tools\cards.json --apply --create-new     # DBに居ない人をその座標で新規登録
```

`cards.json` の形式（`x`,`y` は必須。他は任意）:

```json
[ { "card": "card_001.png", "name": "ゆうご太郎", "x": 512, "y": 730, "power": 644862328, "fcLevel": "FC5" } ]
```

撮影のコツ（実測に基づく）:

- 監視は1周およそ0.8秒。**カードを出したら1秒ほど置いてから次の都市をタップ**すれば取りこぼさない。
- 撮影済みの `card_*.png` は起動時に消さず連番を続ける。要らなくなったらフォルダごと手で消す。
- ★**自分の都市のカードでも名前・X/Y・総力は取れる**（ボタンが「暁の島へ入る/都市強化…」と違うだけ）。
  自分のアカウントは領主ファイルを開けないが、座標と総力はこの経路で拾える。手入力が要るのは FCレベルだけ。
- 撮ったカードは `crop-cards.mjs` で「名前・X/Y・戦闘力」の部分だけ切り出し、数枚ずつ束ねた一覧画像にできる。
  全画面のままチャットに貼るより情報密度が高く、読み取りが速く正確になる。

  ```bash
  node tools\crop-cards.mjs --in tools\cards\cap --out tools\cards\sheets --from 8 --per 8
  ```

検知の仕組み（ここを間違えると黙って取りこぼす）:

カードの見た目は**プレイヤーごとのスキンで色も柄も変わる**（白青/緑/橙…）。明るさや平坦さでの判定も
マップの地面（(183,193,220)・完全に平坦）と区別できない。そこで**スキンで変わらないUI固定色**を使う：

| 手掛かり | 色 | 役割 |
| --- | --- | --- |
| カード左上の杖アイコン | `(13,194,216)` | **決め手。** 全スキン共通で必ず在る |
| 下部ボタンの青 | `(79,165,252)` | カードである裏付け（**1個でよい**） |
| 上端HUDの明るさ | 70以上 | モーダルダイアログ（全画面暗転）を除外 |

実測: 都市カード = 杖16px・青ボタン行13前後・HUD117〜125 / 同盟旗カード = 杖2px / マップ = 杖0px /
領主ファイル = 杖0px。カード幅は約410pxでほぼ一定なので、杖の位置から本体の範囲を割り出している。

過去に踏んだ罠（同じ直し方を繰り返さないため）:

- 横位置を固定していた → 左寄りに出たカードを取りこぼし。カードはタップした都市の近くに出るので左右に動く。
- 白青のボディ帯を探していた → **緑スキンのカードを拾えない**。
- 「同じ行に青ボタンが2つ」を条件にしていた → 小規模アカウントは「部隊援助」**1個しかボタンが無く**、
  何度タップしても撮れない（りつごろｰ で発覚）。
- 重複判定を全画面差分にしていた → 背景アニメだけで7.6%動き、同じカードを何枚も保存。カード領域限定なら0.0%。
- 静止待ちを全画面差分の収束で待っていた → 背景アニメで永久に収束せず**1枚あたり約6.6秒**を空費し、
  その間のタップを取りこぼす（6タップで3枚しか撮れなかった）。

安全設計:

- **動かすのは `placed=0` のみ。** 既に配置済みの都市の座標は既定では触らず「差分の提示」だけ（反映は `--move-existing`）。
- **フットプリント衝突チェック。** 配置先が他オブジェクト（`anchor` は最小角、占有は `w×h`）と重なるならスキップして一覧に出す（`--force` で強行）。同一実行内での取り合いも見る。
- **緩い一致は総力で確定。** 名前が装飾等でずれても、カードの総力とDBの総力が一致すれば本人とみなして自動反映（許容幅は `--power-tol`、既定は完全一致）。総力も合わなければ *要確認* に回して触らない。
- 総力が動いた人だけ `power_history` に1点追記（日次の全員スナップショットは `apply-ranking.mjs` の役目なので二重に打たない）。
- 配置・移動・改名は `audit_log` に個別記録（キーはアプリ準拠の「X」「Y」「配置」）＋実行要約1行、`actor_email='scrcpy-auto'`。
- 結果は `apply-cards-report.json` に全件残る（衝突・要確認・座標が読めなかったカードを含む）。

## 5. 監視モード：倉庫報酬の自動回収（watch-warehouse.mjs）

都市（ホーム）画面を常駐監視し、**倉庫の上に出るバブル**を見つけたら自動でタップして回収する。
放置しておけば取りこぼさない。対象は2種類：

| 対象 | 出現 | 見た目 | 回収操作 |
| --- | --- | --- | --- |
| 宝箱 | 約10分ごと（回収後カウントダウン） | 白い吹き出しの中に木の宝箱 | 1タップ |
| 缶詰（大盤振る舞い） | 毎日 **9時と21時**・期限12時間 | 白い吹き出しの中にオレンジの缶詰＋下に緑の残り時間 | 2タップ（アイコン→ダイアログの緑「受取」） |

```powershell
. tools\adb-env.ps1                                   # 先に接続情報を環境変数へ
node tools\watch-warehouse.mjs                        # 常駐（既定20秒間隔）。終了は Ctrl+C
node tools\watch-warehouse.mjs --dry                  # タップせず検知だけ（動作確認）
node tools\watch-warehouse.mjs --interval 10 --shots tools\shots\wh --log tools\shots\wh\watch.log
```

主なオプション: `--interval 秒`(通常監視の間隔・既定20) / `--max N`(N回で終了) /
`--shots DIR`(検知フレームをPNG保存) / `--log FILE` / `--no-back`(報酬ダイアログをBACKで閉じない) /
`--test-png FILE`(端末なしで1枚だけ判定・較正用) / `--debug`(候補ごとの実測値を表示)。

### 画面の取得方式（`--cap`）— Wi-Fi で回すなら重要

1回の判定で画面を丸ごと吸い上げるので、**接続の種類で転送方式を変える**。

| 方式 | 都市画面での1枚 | 使うところ |
| --- | --- | --- |
| `raw` | **4.43MiB** / 2430ms | USB。端末側の圧縮もホスト側のデコードも無いので最速 |
| `png` | **1295KB** / 1621ms（約3.5分の1） | Wi-Fi。回線が荒れるほど差が開く（raw は1枚54秒＋接続断の実績あり） |

```powershell
node tools\watch-warehouse.mjs                 # --cap auto（既定）: Wi-Fi→png / USB→raw を自動選択
node tools\watch-warehouse.mjs --cap png       # 明示指定
node tools\watch-warehouse.mjs --cap-timeout 10  # 転送が詰まったときの打ち切り秒数（既定15）
```

`auto` は接続先シリアルが `IP:ポート` 形式かどうかで判定する。起動時のログに選択結果が出る。

★ **Wi-Fi で `raw` を使ってはいけない。** 実測でPNG の33倍の転送量になり、1枚54秒かかった末に接続が切れた。

**タイムアウトと自動復旧**: 転送は `--cap-timeout`（既定15秒）で打ち切る（Wi-Fi が詰まると adb は返ってこない）。
連続失敗すると自動で復旧を試みる — 3回目に `adb reconnect`、6回目以降（6の倍数）は Wi-Fi なら
`adb connect <serial>` で繋ぎ直す。20回連続で失敗したら従来どおり終了する。復旧の試行はログに残る。

検知ロジック（`findBubble` 等）は `{width,height,data}` の RGBA しか見ていないので raw / png で結果は変わらない。
較正用の `--test-png` が最初から PNG を同じ形で食わせているのと同じ経路。

### 監視のリズム（逆算してアイドルする）

倉庫は回収するとカウントダウンが始まり、一定周期（実測 約10分）で次の宝箱が出る。
**回収した瞬間から次の出現時刻は計算できる**ので、ずっと20秒ごとに撮り続ける必要はない。

```
起動 → 通常監視(20秒間隔)で1個目を回収
     → 次回を逆算して アイドル（画面を撮らない・約9分）
     → 出現30秒前から 高速監視(3秒間隔) → 出た直後に回収
     → 回収時刻から また逆算 …（周期は毎回の実測で更新）
```

缶詰（9時/21時）は宝箱のアイドル中でも**その時刻に必ず起きて**取りに行く（`--can-hours` / `--can-window`）。
期限が12時間あるので、その場で見つからなくても以後の監視で拾える。

実測ログ（2026-07-26）:

```
20:55:37 宝箱を検知 → タップ（通常監視。見込み20:55:17の20秒以内）
20:55:49 回収。次は 21:05:49 頃の見込み → 待機（約9分半、画面を撮らない）
21:05:48 宝箱を検知 → タップ（高速監視。見込みとの差 1秒）
21:05:59 周期を実測で更新: 600秒 → 593秒
```

関連オプション: `--cycle 秒`(周期の初期見積り・既定600) / `--lead 秒`(何秒前から高速監視・既定30) /
`--fast 秒`(高速監視の間隔・既定3) / `--max-wait 秒`(見込みを過ぎてこれだけ出なければ通常監視へ戻す・既定300) /
`--no-schedule`(逆算せず常に `--interval` で回る従来動作) / `--cooldown 秒`(逆算しない時の回収後の休止・既定60) /
`--can-hours 9,21`(缶詰の出現時刻) / `--can-window 秒`(その時刻から何秒間は高速で探すか・既定300) / `--min-can`。

- 周期の学習は**高速監視で捕まえた回だけ**を採用する。通常監視で捕まえた回は検知が最大20秒遅れるため、
  それを周期として覚えると見込み時刻が毎回後ろへずれていく。
- 手で回収された等で見込み時刻に出なかった場合は、`--max-wait` 秒待ってから通常監視に戻る（取りこぼさない）。
- タップ後もバブルが残っていた（＝回収できていない）回は、逆算の起点にしない。

前提と注意:

- ゲームを**都市（ホーム）画面**にしたまま放置する。倉庫が画面内に入っていること。
- scrcpy は `--stay-awake` で起動しておく。画面が消えると adb 接続ごと落ちる。
- **位置もズームも決め打ちしない。** 画面全体から色で探すので、マップを少しドラッグしても、
  ズームを変えても追従する（実測: 0.5〜1.3倍で検知継続）。上端HUDと下端タブバーは対象外。
- 誤タップ除け: ①バブルは揺れるアニメなので0.7秒あけて2フレーム連続で同じ位置に見えたときだけ叩く
  ②画面が暗転している（ダイアログが開いている）間は何もしない ③タップ後にバブルが消えたかを確認し、
  消えていなければ「倉庫以外を叩いた可能性」を警告として出す。
- 回収時に報酬ダイアログが開く場合は BACK で閉じる（`--no-back` で無効化）。

検知の較正値（`--debug` で同じ数字が出る。720x1612・都市画面での実測）:

| 対象 | 芯px | タンpx | 周りの白率 | 判定 |
| --- | --- | --- | --- | --- |
| 倉庫の宝箱バブル（木部） | 1137 | 62 | 0.395 | ○ chest |
| 缶詰バブル（暗オレンジ） | 407 | 31 | 0.375 | ○ can |
| 探検の地図バブル | 443 | 1493 | 0.521 | ✕（タンが芯の0.6倍以上＝羊皮紙） |
| マップの木製建物・橋 | 772 | 0 | 0.002 | ✕（白い吹き出しに載っていない） |
| 大盤振る舞いダイアログ内の缶アイコン | — | — | 0.010〜0.034 | ✕（青タイルの上なので白くない） |

宝箱と缶詰を分けるのは **b（青）成分**：缶詰 `b=0〜9` / 宝箱 `b=39〜54`（g も 44〜74 対 93〜110 で離れている）。

過去に踏んだ罠:

- 芯の塊の範囲を16pxセル単位のまま測っていた → 同じ絵でもグリッドの切れ目次第で箱が最大15px膨らみ、
  周囲の白率が 0.51→0.30 に振れて**ドラッグでずらしただけの画面を取りこぼした**。範囲は芯ピクセルの実位置で測り直す。
- 白率を測る余白を固定px（14px）にしていた → ズームで壊れる。余白は塊の大きさに比例させる。
- 缶詰の判定を宝箱と同じ余白(0.22倍)で測った → **白率0.048で検知できない**。缶詰はアイコンが吹き出しいっぱいに
  描かれているので、白を測る輪を離す（0.70倍・芯ボックスの内側は見ない）。実測 0.22→0.069 / 0.60→0.360 / 0.80→0.370。
- 缶詰の色条件を `b<=48` と緩く書いた → **宝箱の影を缶詰と誤判定**（宝箱バブルで芯367pxを拾った）。`b<=20` で分離。

## 総力の履歴（power_history）との整合 ★重要

アプリは総力の更新時に `power_history` テーブルへスナップショットを追記する（API内で実施。`source` は `manual` / `scrcpy`）。推移グラフはこの履歴を使う。本ツールは D1 を直接書くため、同じ追記を自前で行い整合させる：

- `apply-ranking.mjs` … `power_history` の有無を自動判定し、あれば `source='scrcpy'` で履歴も追記。
- `ranking-to-sql.mjs` … `update.sql` / `new-cities.sql` に履歴INSERTを同梱（`--no-history` で無効化可）。

前提：本番 D1 に `schema/0009_power_history.sql` が適用済みであること。未適用なら先に
`wrangler d1 execute snw-map-gen2 --remote --file=schema/0009_power_history.sql` を実行する。

## 注意

- APIトークンは秘密情報。環境変数で渡し、リポジトリにコミットしない（`.gitignore` 済みの領域で扱う）。
- `power` は仕様上「都市（CITY）」向けの項目。HQ等に名前がある場合も名前一致すれば対象になるので、必要なら `type` で絞る運用に調整可。
- 照合は名前依存のため、改名・表記ゆれで未一致が出る。レポートの「未一致」「要確認」を人が確認するのが前提の半自動フロー。
